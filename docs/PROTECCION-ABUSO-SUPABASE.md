# Protección de ingresos y configuración perimetral

En la API se conservan los límites atómicos por identidad y por código compartido. El contador por código limita simultáneamente solicitudes de alta y recuperación de todas las identidades; no pretende identificar IP ni ser una solución contra ataques distribuidos. Los accesos cruzados siguen condicionados a identidad Auth, membresía y capacidad aleatoria; los fallos del almacén deniegan la operación. El presupuesto por código puede bloquear una sala bajo ataque; supervisarlo y ajustar ventanas con pruebas de concurrencia antes de habilitar aulas reales. Los límites por sala no sustituyen a un control de perímetro.

Supabase Auth aplica de forma administrada límites por IP al alta anónima y a autenticación (ver https://supabase.com/docs/guides/auth/rate-limits). No se utiliza `X-Forwarded-For`, `CF-Connecting-IP` u otra cabecera cliente en la función: no se ha verificado un contrato que garantice su reemplazo por el proxy de entrada. No habilitar `Sb-Forwarded-For` salvo que una arquitectura proxy verificada use una clave secreta en servidor y elimine cualquier cabecera de cliente.

La interfaz incorpora Turnstile de ejecución explícita, con aparición solo si el proveedor pide interacción. Una solicitud Auth obtiene un token fresco y lo pasa a Supabase, que realiza la validación. Si la generación falla, no se envía la solicitud. Antes de activar registro anónimo en el proyecto alojado:

1. Crear un widget Turnstile administrado para el dominio exacto `joelcastiss.github.io`; colocar solo su *site key* pública en `public/captcha-config.js`. Mantener la clave secreta del proveedor exclusivamente en la configuración de Auth. Revisar las condiciones y consentimiento aplicables al proveedor.
2. Activar Turnstile en Supabase Auth > Bot and Abuse Protection y configurar límites IP para anónimos, signup/login, recuperación, verificación y renovación. Elegir cuotas atendiendo a grupos que comparten la misma IP de aula; no asumir que el valor predeterminado es apropiado. Evitar activar CAPTCHA sin publicar simultáneamente la site key, pues bloquearía el acceso.
3. Verificar el origen, CSP (`script-src` y `frame-src` para `https://challenges.cloudflare.com` si hay CSP), comportamiento de bloqueo/expiración/reintento y que ninguna clave secreta llega al cliente. Probar docente y estudiantes con CAPTCHA exigido en un entorno separado y con las claves de prueba oficiales de Cloudflare antes de usar claves reales.
4. Ejecutar `scripts/verify-supabase-auth-guard.mjs` con `SIDE_LITE_SUPABASE_MANAGEMENT_TOKEN` de solo lectura. El script consulta exclusivamente el proyecto SIDE-LITE y muestra únicamente hallazgos, no secretos. Una auditoría aprobada comprueba que Auth anónimo, CAPTCHA, site key y límite IP están declarados; no prueba la identidad de IP, la cuota apropiada ni la entrega real.
5. Añadir protección gestionada en el gateway para `/functions/v1/side-lite-api/api/join` y `/api/guest/recover` que use la IP observada por la infraestructura y no una cabecera suministrada por clientes; restringir o acreditar que no pueda evitarse invocando directamente el endpoint de Supabase. No exponer el servicio como listo hasta verificarlo con tráfico real controlado.
