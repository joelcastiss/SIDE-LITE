# Plan de pruebas de Neon aislado

**No ejecutar hasta autorizar expresamente los recursos y confirmar proyecto y rama.** Una rama puede heredar cuentas, sesiones y datos del padre. Confirmar mediante el proveedor que el ID corresponde al proyecto SIDE-LITE, que la rama es nueva y contiene solo datos sintéticos, que sus funciones, Auth y disparadores apuntan a ella, y que no es ninguna rama de SIDE1 ni la rama de desarrollo existente. La comprobación del nombre o la URL no demuestra el aislamiento.

La prueba `e2e/neon-isolated-browser.spec.js` está desactivada por defecto y exige una función web HTTPS cuyo host empiece por el ID de la rama y termine en `.neon.tech`. Es compatible solo con la puerta de vista previa y la interfaz BFF existentes; si cambia el alojamiento, habrá que adaptar y revisar las comprobaciones antes de ejecutarla. Las funciones actuales fijan los hosts de desarrollo y no están preparadas para una nueva rama sin configuración y revisión de seguridad.

Preparar tres identidades sintéticas autorizadas (docente, estudiante A, estudiante B) y guardar un archivo JSON **solo bajo `tests/output/`** con la forma `{"gateKey":"...","users":[{"email":"...","password":"..."},{"email":"...","password":"..."},{"email":"...","password":"..."}]}`. No guardar credenciales en el repositorio, ni adjuntar capturas, trazas, salidas o informes que contengan sesiones o claves. Prever el ciclo de vida y la retirada de datos de prueba sin actuar sobre otras ramas.

En PowerShell, una vez autorizado y después de preparar el servicio y el cierre, definir `SIDE_LITE_ISOLATED_E2E=1`, `SIDE_LITE_TEST_BRANCH_ID` con el ID confirmado, `SIDE_LITE_TEST_ORIGIN` con el origen HTTPS completo y `SIDE_LITE_TEST_IDENTITIES` con la ruta del archivo ignorado. Ejecutar `npx playwright test e2e/neon-isolated-browser.spec.js --workers=1`. Los dos primeros escenarios completan tres y seis ciclos con dos estudiantes mediante la interfaz; el tercero comprueba un ciclo real de 120 segundos, no una partida completa de 120 segundos. Requiere un disparador de cierre funcional y tiempo de procesamiento suficiente. El test coteja resultados, clasificación y atributos de cookie, y comprueba recarga de sesión. Una ejecución con identidad y rama reales aún no se ha realizado.

## Comprobaciones adicionales obligatorias

- Con una bandeja de pruebas autorizada y la configuración real de correo, registrar una cuenta, verificar que el código llega, que el código incorrecto o vencido falla, que antes de verificar el correo no entra a la API y que después sí. No copiar el código al informe.
- Comprobar alta docente explícita autorizada, denegación sin alta y revocación efectiva en una sesión abierta. El correo institucional verificado no demuestra por sí solo la condición de docente.
- Verificar logout, revocación de sesión, recarga y que una cuenta no puede acceder a partidas de otras. Repetir con cookies manipuladas, CSRF y caducidad; auditar la integración HTTP propia frente al SDK soportado.
- Probar concurrencia y duplicación del cierre, caídas y recuperación después del reinicio del backend y de la base, y medir demora real desde los 120 segundos. Comprobar límites de tiempo, costes y reintentos del programador.
- Comprobar que los logs e informes no contienen credenciales, cookies, datos personales o tokens; registrar solo resultados y versión. No usar estudiantes reales hasta autorizar la publicación.

## Preinspección de PostgreSQL de la rama designada

Se preparó `e2e/neon-branch-preflight.js` para la rama `br-bold-king-bc32g1vs`; por defecto no se conecta. Tras confirmar en el plano de control que el proyecto es SIDE-LITE, el endpoint directo corresponde exactamente a esa rama y el rol es apropiado, se puede habilitar exclusivamente una preinspección de lectura mediante `SIDE_LITE_READONLY_PREFLIGHT=1`, `SIDE_LITE_CONFIRMED_BRANCH=br-bold-king-bc32g1vs`, `SIDE_LITE_CONFIRMED_ENDPOINT` y `SIDE_LITE_ISOLATED_DATABASE_URL`. No incluir ni mostrar la URL de conexión en comandos, informes, logs o Git. La comprobación de host es una defensa adicional: **no demuestra la identidad del proyecto o rama**. El script abre una transacción READ ONLY y consulta únicamente existencia de esquemas y objetos, sin leer correos ni sesiones. No modifica nada; conexión y transacción todavía no se han probado contra Neon.

Para aplicar migraciones y probar escrituras hace falta autorización separada y verificar los recursos y la composición heredada: la migración inicial exige `neon_auth."user"`, las migraciones docentes asumen columnas `email`, `emailVerified` y `banned`, y los grants exigen un rol `lite_dev_api` ya existente. El rol y el esquema Auth deben inspeccionarse, no crearse ni alterarse a ciegas. El SQL para entorno local crea identidades Auth simuladas y no se debe ejecutar contra Auth administrado. Antes de cualquier prueba de escritura, acordar qué datos de ensayo crear, cómo identificarlos y limpiarlos, y verificar que no haya ciclos vencidos ajenos: `closeDue()` opera sobre todos los ciclos vencidos de la rama, no solo sobre un fixture dado.

Las pruebas de concurrencia deben ejecutar cierres simultáneos sobre dos empresas, comprobar un resultado por empresa, reintentar tras un fallo y verificar integridad tras reiniciar un proceso y una conexión. No validar reinicio de base desconectando servicios existentes; realizarlo solo en recursos de ensayo aprobados. Las pruebas de correo y revocación requieren usuarios reales de prueba y acceso autorizado a una bandeja, nunca insertar directamente filas ficticias en `neon_auth` de un servicio administrado.
