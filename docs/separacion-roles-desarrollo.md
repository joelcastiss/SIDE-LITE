# Separación de roles de desarrollo

`202611080002_separate_closer_privileges_dev.sql` prepara una separación de privilegios para un entorno SIDE-LITE aislado. Presupone roles distintos `lite_dev_api` y `lite_dev_closer`, ya creados como NOINHERIT, sin pertenencias privilegiadas ni propiedad de objetos y sin superusuario ni BYPASSRLS. Deben tener credenciales distintas, privadas y limitadas al entorno. No contiene contraseñas, no crea roles y no configura ni despliega servicios. Aplicarla después de las migraciones anteriores, en la misma transacción y únicamente con la aplicación de cierre configurada para el nuevo rol. Verificar antes los privilegios efectivos, incluido PUBLIC y membresías, y después probar API y cierre con los roles reales.

La migración revoca a la API la modificación del identificador de perfiles y la escritura directa de resultados, de caja e inventario, y del estado del ciclo. El rol de cierre puede leer los datos necesarios, crear resultados y actualizar exclusivamente estado del ciclo y caja/inventario. PostgreSQL exige algún privilegio UPDATE para `SELECT FOR UPDATE`; se concede a la API UPDATE sobre `lite_cycles.id` para conservar el bloqueo de decisiones. La API mantiene otros privilegios, entre ellos inserción y actualización de decisiones, inserción de empresas y UPDATE sobre identificadores de partidas y ciclos, necesarios o heredados de la implementación actual.

**Riesgo residual:** los permisos SQL no imponen aislamiento por usuario. Con la credencial de API comprometida, un atacante podría leer datos de distintas partidas, insertar empresas con saldos arbitrarios, modificar decisiones ajenas o alterar identificadores allí donde el privilegio UPDATE lo permita. Los permisos de bloqueo sobre columnas no equivalen a una función que solo bloquee. La API no debe considerarse protegida ante compromiso de sus propias credenciales; no se han implementado políticas RLS. Para reducir este riesgo se requiere rediseñar el acceso mediante funciones acotadas o autorización de base de datos por identidad y verificar su seguridad, sin confiar únicamente en la capa de aplicación. El rol de cierre también puede modificar partidas ajenas a través de los campos que necesita: mantener su credencial y función inaccesibles a clientes y proteger la invocación del trigger.

`e2e/separate-roles-isolated.js` verifica las concesiones y ejecuta `closeDue` con el rol de cierre en PostgreSQL local desechable. Solo acepta una base vacía localhost llamada `side_lite_roles_test`, necesita un clúster desechable y crea roles de prueba; nunca apuntar a una base remota o compartida. La prueba no establece compatibilidad con roles reales de Neon, despliegue, privilegios heredados ni seguridad de producción. La provisión de roles, conexiones y su despliegue aún debe planificarse y probarse en la rama aislada autorizada.

El puente local Neon `remote/dev-server.js` requiere dos URLs independientes: `NEON_DATABASE_URL` para `lite_dev_api` y `NEON_CLOSER_DATABASE_URL` para `lite_dev_closer`. Ambas deben apuntar al endpoint de desarrollo permitido por `NEON_DEV_DB_HOST`; la aplicación valida el usuario declarado y `current_user` de cada conexión antes de escuchar y usa solo el pool de cierre para procesar ciclos. Los secretos se proporcionan por entrada estándar a `remote/dev-runner.js`, no como argumentos ni archivos versionados. Las credenciales, membresías y permisos efectivos de cada rol siguen requiriendo verificación en el entorno aislado. El puente está fijado a la rama de desarrollo documentada y no sirve como despliegue de producción.
