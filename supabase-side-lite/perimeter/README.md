# Prototipo de perímetro: no desplegado

Este prototipo está separado de la API actual: **no protege producción por sí solo**. La integración debe hacerse de forma coordinada, o el ingreso dejará de funcionar. El servidor `proxy.js` está pensado para escuchar HTTPS directamente en un servicio con IP pública; TLS termina en el proceso Node y `req.socket.remoteAddress` identifica la conexión. No se debe poner tras balanceador, CDN, proxy de desarrollo ni ninguna ruta que altere esa propiedad. Hay que comprobar el aislamiento de red y que no exista otra vía de entrada al proceso. Un proxy intermedio haría que clientes compartan un límite o que la IP identificada sea incorrecta. IPv6, NAT y redes escolares compartidas requieren medir y ajustar el límite de 60 intentos por cinco minutos.

La API debe exigir `createIngressGuard` para toda petición POST a `/api/join` y `/api/guest/recover` **antes** de procesar el cuerpo, fallando cerrada si falta el secreto o falla PostgreSQL; no basta con redirigir el navegador al proxy, ya que la URL Supabase seguiría accesible. El guard verifica HMAC, hora, nonce, ruta, cuerpo y credenciales y usa `postgresNonceConsumer` para rechazar la repetición. Firmas tienen una vigencia máxima de 30 segundos. Todos los demás métodos o rutas deben continuar con las reglas actuales. El ejemplo no está conectado al adaptador: requiere revisión, pruebas completas y cambio del cliente para usar el proxy para ambas rutas.

Provisionar un servicio HTTPS con certificado válido y secreto aleatorio de 32 bytes codificado en 64 caracteres hexadecimales, compartido exclusivamente entre proxy y función; almacenar y rotar como secreto del proveedor. Otorgar al rol restringido del proxy solamente los permisos de la tabla de ventanas y al rol de API solamente `INSERT` y `SELECT` de nonces. `schema.sql` es un borrador, no una migración aplicada. Mantener relojes sincronizados, límites de conexión y tamaño, tráfico saliente restringido al proyecto Supabase, monitoreo y borrado periódico de nonces expirados y ventanas antiguas mediante una tarea privilegiada. No registrar ni almacenar IP en claro: el prototipo guarda un HMAC de IP. Definir la política de retención, notificar caídas del limitador y medir la carga antes del despliegue.

El host debe ejecutar el handler con `node:https.createServer` y TLS directo; nunca usar `x-forwarded-for`, `x-real-ip` ni cabeceras `cf-*` como IP. Configurar firewall, DNS y un proveedor adecuado no está resuelto en este repositorio. La prueba automatizada `node --test tests/perimeter-prototype.test.js` valida contrato, falsificación, repetición y fallo cerrado usando almacenamiento simulado; no demuestra el perímetro real ni reemplaza una prueba de red contra el despliegue. El límite depende de que el servicio y PostgreSQL estén disponibles y el acceso directo a la función esté protegido por el guard.
