# Límite de intentos de código: preparación

`createJoinLimiter({pool})` implementa el contrato `limitJoin({userId})` del servicio de partidas: diez intentos por cuenta verificada por ventana fija de cinco minutos. El contador se comparte en PostgreSQL y la operación es atómica ante peticiones concurrentes. Un fallo de conexión se propaga y debe cerrar la petición; nunca activar un modo que permita intentos cuando falle la base. El identificador procede únicamente del JWT verificado por el servidor. El módulo está preparado pero no está conectado a un servidor ejecutable ni desplegado.

Una ventana fija permite hasta veinte intentos alrededor de su cambio. Este límite no evita intentos distribuidos entre múltiples cuentas. Antes de habilitar el servicio hay que añadir un límite independiente por IP en una capa perimetral de confianza, sin confiar en `X-Forwarded-For` suministrado directamente por el navegador; documentar configuración del proxy, política de retención y privacidad. No implementar bloqueo global por IP sin considerar redes compartidas.

El contador vive en tabla privada con RLS y sin acceso `anon` o `authenticated`. El servicio necesita un rol de base de datos restringido; la migración concede temporalmente acceso a `service_role` y requiere revisión de privilegios antes de cualquier despliegue. La tabla contiene un registro por usuario que intentó acceder, eliminado cuando se borra el usuario; valorar política de limpieza para cuentas inactivas. No usar el valor del código ni IP como identificador en logs.

Para la prueba `supabase-side-lite/tests/join-limiter-postgres.test.mjs` utilizar PostgreSQL local vacío desechable, aplicar el bootstrap de Auth simulado, migración principal y migración de limitador en ese orden. Definir `SIDE_TEST_DISPOSABLE=YES` y `SIDE_LITE_TEST_DATABASE_URL` apuntando solo al localhost, y ejecutar `node --test supabase-side-lite/tests/join-limiter-postgres.test.mjs`. Esta prueba no confirma configuración de Supabase real ni el límite IP de producción.
